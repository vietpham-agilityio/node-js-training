# node-js-training

A NestJS microservices practice project. Nest CLI monorepo (not Nx), package manager is **pnpm**.

## Layout

```
apps/
  order/              HTTP + TCP microservice. TypeORM+SQLite persistence.
  inventory/           TCP-only microservice (no HTTP). TypeORM+SQLite persistence.
  user/                HTTP + TCP hybrid app, TypeORM+SQLite, Swagger, URI versioning (v1/v2).
  product/             HTTP app, TypeORM+SQLite, Swagger, URI versioning (v1/v2).
  auth/                TCP-only microservice (no HTTP), no persistence. Issues/signs JWTs; owns nothing, delegates the credential check to `user`.
  api-gateway/         HTTP app. Proxies to `order`, `inventory`, `user`, `product`, `auth`. Sole client-facing entry point.
libs/
  common/    Cross-cutting primitives: filters, interceptors, guards, decorators, middleware, JWT key util. @app/common
  constants/ Shared event names + shared domain shapes. @app/constants
```

Registered Nest CLI projects (`nest-cli.json`): `constants`, `common` (libraries), `api-gateway`, `inventory`, `order`, `user`, `product`, `auth` (applications). The default (unnamed) `nest-cli.json` project points at `api-gateway`.

**Hard rule: apps never import from another app's `src/`.** Anything shared between apps belongs in `libs/*` and is consumed through a `@app/*` path alias. Adding a new alias means updating three places together:
1. `tsconfig.json` → `compilerOptions.paths`
2. root `package.json` → `jest.moduleNameMapper`
3. `nest-cli.json` → `projects` (if it's a new lib)

(`api-gateway`'s `OrderProxyService`/`ProxyController` and `UserProxyService`/`UserProxyController`/`ProductProxyService`/`ProductProxyController` are a known, accepted exception — see "Known, intentional limitations". These bare `apps/<app>/src/...` imports resolve under `nest build` via `tsconfig.json`'s `baseUrl`; root `package.json`'s `jest.modulePaths: ["<rootDir>"]` mirrors that so the same imports also resolve under Jest.)

## Running

Package manager is pnpm. Nest CLI monorepo mode: `nest build`/`nest start` alone only target the default project (`api-gateway`). To build every project: `npx nest build --all`. To run one app: `npx nest start <project> --watch` (e.g. `npx nest start order --watch`).

**Docker**: root `Dockerfile` is a single multi-stage build parameterized by `--build-arg APP=<project>` (any application name from `nest-cli.json`, not the `constants`/`common` libraries — those get inlined by webpack into whichever app bundles them). `docker-compose.yml` builds and runs all six apps together, wiring the TCP client host env vars (below) to each other's Compose service name and the HTTP proxy base URLs to `http://<service>:<port>`. Needs a real `.env` at repo root (copy `.env.example`) for the JWT keypair — `docker compose up --build` to run the whole stack, `curl -k https://localhost:3002/health` to confirm the gateway's up — Compose mounts `./certs` and sets `TLS_*`, so the gateway is HTTPS on both the dev and prod paths (see "Transport security" below). See `docs/adr/0012-containerize-with-docker-compose.md` for why the Dockerfile is single/parameterized rather than one per app, and why `pnpm` is pinned to a specific version in it (a newer pnpm silently ignored `onlyBuiltDependencies` and broke native module builds for `better-sqlite3`/`bcrypt`).

**Kubernetes**: tried and reverted 2026-08-04 — Docker Compose is the day-to-day workflow for now. A full set of manifests (namespace, ConfigMap, per-app Deployments/Services/PVCs, `api-gateway`'s HPA) was built, deployed to Docker Desktop's built-in Kubernetes, and smoke-tested end to end before being removed. The design (ConfigMap for centralized config, K8s Service DNS, per-app replica pinning around the SQLite-per-pod constraint) is preserved as a historical record in `docs/adr/0013-kubernetes-manifests.md`'s "Reversion" section if this gets picked back up later.

|------------------|-----------|----------|-----------------------------------------------------------------|

| order            | 3001      | 8001     | create/list/update/delete orders                               |

Testing: `pnpm test:unit` (unit, co-located `*.spec.ts` across every app — including `api-gateway`'s proxy service/controller/health controller coverage), `pnpm test:cov`, and four per-app e2e scripts — `pnpm test:e2e:order`, `test:e2e:user`, `test:e2e:product`, `test:e2e:inventory` — each running that app's own `test/jest-e2e.json` against its real CRUD/TCP routes. `inventory`'s is real coverage, not a stub: it exercises both the `UPDATE_STOCK` TCP message pattern and the full `order_created`→stock-decrement→`ORDER_PROCESSED` event flow. `auth` has no e2e suite (no persistence, no HTTP surface of its own to exercise). Jest config is centralized in root `package.json` (`roots: apps/, libs/`, `@app/*` aliases mirrored in `moduleNameMapper`, `setupFiles: ["dotenv/config"]` so `.env` is loaded before tests run). Each app's own `test/jest-e2e.json` duplicates that same `moduleNameMapper`/`setupFiles` since it's a separate Jest config, not the root one.

CI (`.github/workflows/ci.yml`) runs on push/PR to `feat/*` branches: parallel `lint` (`eslint`), `build` (`nest build --all`), and `test` jobs. The `test` job generates an ephemeral RS256 keypair inline via a one-line `node -e` script and appends it to `$GITHUB_ENV` (CI has no `.env`), then runs `test:unit` plus all four `test:e2e:*` scripts.

Nothing loads `.env` automatically except through `dotenv`: it's a plain dependency (not `@nestjs/config`, which this repo deliberately doesn't use), loaded via `import 'dotenv/config'` at the top of each app's `main.ts` that reads env vars, and via Jest's `setupFiles` for tests. `api-gateway` reads `ORDER_SERVICE_BASE_URL`/`USER_SERVICE_BASE_URL`/`PRODUCT_SERVICE_BASE_URL` (used by `OrderProxyService`/`UserProxyService`/`ProductProxyService` to build each downstream base URL) — each falls back to `http://localhost:3001`/`3003`/`3004` (`libs/constants/src/shared/router/route.ts`) when unset, so the gateway boots without a `.env` in CI/local dev; Docker Compose still overrides them to each service's Compose name. `auth`, `user`, `product`, and `api-gateway` all read `JWT_PRIVATE_KEY_BASE64`/`JWT_PUBLIC_KEY_BASE64` (see "Authentication & authorization" below) — `.env` is gitignored, `.env.example` documents the shape and a one-line keygen command. `user`/`product` also read `REDIS_URL` (see "Response caching" below), optional everywhere except Docker Compose. **Because `dotenv/config`'s default behavior resolves `.env` relative to `process.cwd()`, always run/test from the repo root** (`npx jest --config apps/user/test/jest-e2e.json`, not `cd apps/user && npx jest ...`) — running from a subdirectory silently loads no `.env` at all rather than erroring, which reads as a JWT/signing failure with a confusing stack trace.

## Transport security

TLS terminates **in `api-gateway` and nowhere else** — it's the sole client-facing entry point (ADR 0005), so it owns the one hop that crosses a real network. `user`/`product`/`order` stay plain HTTP behind it; `inventory`/`auth` are TCP-only and have no HTTP server at all. See `docs/adr/0017-tls-in-api-gateway-and-helmet-headers.md`.

HTTPS is **opt-in via env vars, not a code branch**: `loadHttpsOptions()` (`@app/common`) reads `TLS_KEY_PATH`/`TLS_CERT_PATH` and returns `undefined` when either is unset, which makes `NestFactory.create` fall back to `http.createServer`. So cert-less local dev and the e2e suites just work, and `api-gateway/src/main.ts` has one unconditional call site. A path that *is* set but unreadable throws rather than silently downgrading to HTTP. Certs live in a gitignored `/certs` — generate a self-signed pair with the `openssl` command in `.env.example`. Compose bind-mounts `./certs:/app/certs:ro` on `api-gateway` only; the `Dockerfile` doesn't know about certs.

`applySecurityHeaders(app, { httpsEnabled })` (`@app/common`) wraps a single `helmet()` call and is registered in all four HTTP apps' `main.ts`, **before** `SwaggerModule.setup` and `VersionManagementMiddleware` so `/api-docs` and `/health` get the headers too.

Three traps worth knowing:

- **`import helmet from 'helmet'`, not `import * as helmet`.** Helmet 8 is a default export; the `import * as` form from the Nest 7-era docs yields a non-callable namespace under this repo's `esModuleInterop`/`nodenext`. Same stale-docs shape as the `CacheModule` trap above. And bare `helmet()` is the right call — `helmet.hsts()` alone ships 1 header instead of ~12.
- **HSTS is host-scoped and ignores the port.** Emitting it from `https://localhost:3002` pins *every* localhost port for `maxAge`, so `http://localhost:3003/api-docs` and `:3004` get force-upgraded to HTTPS, fail, and stay broken until cleared via `chrome://net-internals/#hsts`. That's why it's gated to `httpsEnabled && NODE_ENV === 'production'`. Both Compose paths serve HTTPS (`TLS_*` and the `./certs` mount are in the base file), but only one emits HSTS: a plain `docker compose up` merges `docker-compose.override.yml` and runs `NODE_ENV: development` (HSTS off — right answer for localhost), while `pnpm docker:prod` skips the override and runs `production`, where HSTS **is** live. Smoke-test that one with `curl -k`, never a browser.
- **CSP is at helmet's defaults, `script-src 'self'` included — don't widen it "for Swagger".** The usual advice to add `'unsafe-inline'` doesn't apply on `@nestjs/swagger` 11, which serves its bootstrap as an external `swagger-ui-init.js`; the only inline content is a `<style>`, already covered by the default `style-src`. Verified by rendering `/api-docs` under the strict policy with no console violations, and there's a spec asserting `script-src` stays un-widened.

## Response caching

`user` and `product` cache their GET routes (`findAll`/`findOne`) via `@nestjs/cache-manager`'s `CacheInterceptor`, applied per-route with an explicit `@CacheKey(...)` rather than globally — see `docs/adr/0016-redis-response-cache-for-user-product.md`. **The old `import { CacheModule, CacheInterceptor } from '@nestjs/common'` (Nest 7/8-era) no longer exists on Nest 11** — the module lives in `@nestjs/cache-manager`, wrapping `cache-manager` v7's Keyv-based rewrite. That rewrite also dropped the old in-memory store's `max` (LRU capacity) option; there's no cap on the default in-memory store today, and a bounded/shared store means supplying an explicit Keyv-compatible `stores` entry yourself.

`libs/common/src/cache/app-cache.module.ts` (`AppCacheModule`, `@app/common`) centralizes this: it points at Redis via `@keyv/redis`'s `createKeyv(process.env.REDIS_URL)` when `REDIS_URL` is set and `NODE_ENV !== 'test'`, and otherwise passes no `stores`, which makes `cache-manager` fall back to its own (unbounded, per-process) in-memory store — same fallback shape as each app's `TypeOrmModule.forRoot` swapping to `:memory:` under `NODE_ENV=test`. Only `user`/`product` import `AppCacheModule`; `order`/`inventory`/`auth`/`api-gateway` don't. `ProductService`/`UserService` inject `CACHE_MANAGER` directly and delete the relevant cache key(s) on `create`/`update`/`remove` so writes are visible on the next read rather than waiting out the TTL. Docker Compose runs a `redis:7-alpine` service that only `user`/`product` depend on.

**`DEFAULT_CACHE_TTL_MS` is in milliseconds** (cache-manager v7/Keyv take ms, not seconds). Setting it to a seconds-looking value like `600` yields a 0.6s TTL, which presents as "caching is broken" — every request returns `X-Cache: MISS` because entries expire between manual test requests.

Cache status is observable **through `api-gateway`** rather than only by hitting `user`/`product` directly, since the gateway is the sole intended entry point (ADR 0005). `HttpProxyService.forward()` copies the downstream `X-Cache` header onto the gateway's own response; the gateway's proxy controllers get that response object via `@Res({ passthrough: true })` (the `passthrough` flag is required — a bare `@Res()` puts Nest in manual-response mode and skips `ResponseLoggingInterceptor`). `forward()`/`withAuth()` live on the shared `HttpProxyService` base class, not copy-pasted per proxy service. To inspect the cache itself: `docker compose exec redis redis-cli KEYS '*'` / `GET products:all` / `PTTL users:2`, or `MONITOR` to watch `GET`/`SET`/`UNLINK` live.

## Event-driven order ↔ inventory flow

Event names live in `libs/constants/src/constants.events.ts` (`ORDER_EVENTS.ORDER_CREATED`, `ORDER_UPDATED`, `ORDER_PROCESSED`). Shared `Order`/`OrderStatus` shape lives in `libs/constants/src/shared/interfaces/order.ts` — `apps/order/src/order.entity.ts`'s `Order` class implements that interface (and is also a TypeORM `@Entity`); don't reintroduce a lib → app dependency by re-exporting an app's entity from `libs/constants`.

Flow: `POST /orders` on `order` (3001) → `OrderService.createOrder` persists the order via its `Order` repository, then emits `ORDER_CREATED` over TCP to `inventory` (8002) → `InventoryController` (`@EventPattern`) → `InventoryService.handleOrderCreated` checks stock in its own `InventoryItem` repository, emits `ORDER_PROCESSED` back to `order` (8001) → `OrderController` (`@EventPattern`) is meant to update the order's status via `OrderService.handleOrderProcessed`.

The return leg (`ORDER_PROCESSED` reaching `order`) does update order status — confirmed via a Docker Compose smoke test 2026-08-03 (`order`'s status flips `Pending` → `Completed` after the round trip through `inventory`, cross-container). An earlier version of this doc described this as a known unfixed bug; that was stale by the time it was checked.

## Authentication & authorization

`auth` (TCP-only, port 8003, see `docs/adr/0008-dedicated-auth-app-rs256.md`) is the only thing that can issue a valid JWT. It signs with `JWT_PRIVATE_KEY_BASE64` (RS256); every other app that guards routes (`user`, `product`, `api-gateway`) registers its own verify-only `JwtModule.registerAsync` with just `JWT_PUBLIC_KEY_BASE64` and checks signatures **locally** — no network call to `auth` on a per-request basis. `order`/`inventory` don't register `JwtModule` since neither applies `AuthGuard` today.

Two flows, both via `api-gateway`'s `AuthProxyController` (`POST /auth/login`, `POST /auth/register`), both TCP-proxied to `auth`, both returning `{ accessToken }`:
- **Login**: `auth` calls `user`'s `USER_MESSAGES.VALIDATE_CREDENTIALS` TCP handler (bcrypt-compares against the hashed password), then signs a token with `{ sub, email, role }`.
- **Register** (public, unguarded — you can't have a token before you have an account): `auth` calls `user`'s `USER_MESSAGES.CREATE_USER` TCP handler, **forcing `role` to `USER_ROLE.USER` server-side** regardless of what the client sent, then signs a token the same way. `POST /users` (guarded) is the separate path for creating a user with an arbitrary role.

`UserEntity.password` is `@Column({ select: false })` — never returned by default `find`/`findOne` queries. `UserService.create`/`update` additionally strip `password` from what they return, since `select: false` doesn't stop `.save()` from handing back whatever was assigned onto the entity before persisting.

`USER_ROLE` (`libs/constants/src/shared/interfaces/user.ts`) is the canonical role enum — `apps/user/src/user.entity.ts`/`user.dto.ts` import it from `@app/constants` rather than defining their own, same pattern as `OrderStatus`.

`api-gateway`'s proxy services (`UserProxyService`, `OrderProxyService`, `ProductProxyService`) do forward the caller's `Authorization` header downstream — each proxy controller reads it via `@Headers('authorization')` and the matching proxy service attaches it to the outgoing Axios request via a private `withAuth()` helper. Guarded routes hit *through the gateway* (e.g. `POST /v1/users`) work the same as hitting the downstream app directly. (An earlier version of this doc described this as an unfixed gap — that was stale by the time it was checked; the forwarding was added alongside RBAC in `5b0c644`.)

## Cross-cutting conventions (`libs/common`, `@app/common`)

- `HttpErrorFilter` — `@Catch(HttpException)` → `{statusCode, message, timestamp, path}`.
- `ResponseLoggingInterceptor` — wraps success responses as `{success, data, timestamp}`. No longer does any logging itself (see `AppLoggerModule` below) — the name is now a slight misnomer, kept for historical continuity. Registered only in `api-gateway` (`app.module.ts`) — `product`/`user` deliberately don't, so a request routed through the gateway gets wrapped exactly once instead of twice (see `docs/adr/0018-drop-response-interceptor-from-product-user.md`). This means a direct call to `product`/`user` on their own port (3003/3004) returns a raw, unwrapped body, while the same call through the gateway returns the wrapped envelope.
- `AuthGuard` — verifies the Bearer token as a real RS256 JWT (`JwtService.verifyAsync`) and attaches the decoded payload to `request.user`. Requires the consuming app to have `JwtModule` registered (see "Authentication & authorization" above) — constructing a module that uses `AuthGuard` without it throws a DI resolution error, including in unit tests (provide a mock `JwtService`).
- `RolesGuard` + `@Roles(...roles: USER_ROLE[])` — authorization on top of `AuthGuard`; compares `request.user.role` against roles set via the decorator; no-ops (allows through) when a route has no `@Roles(...)` metadata. Applied so far to: `POST /products` (create, `ADMIN`-only, both `product`'s own `ProductController` and `api-gateway`'s `ProductProxyController`), `GET /users` + `GET /users/:id` (`ADMIN`-only, both `user`'s own `UserController` and `api-gateway`'s `UserProxyController`), and `PATCH /inventory/:productId/stock` (`MERCHANT`-only, `api-gateway`'s `InventoryProxyController` only — `inventory` itself has no HTTP/`AuthGuard` to attach it to). Every other route remains authentication-only. See `docs/adr/0010-rbac-role-to-route-mapping.md`.
- `decodeBase64Key(value?: string)` — base64→utf8 PEM decode, shared by every app's `JwtModule.registerAsync` factory.
- `AppLoggerModule` (`libs/common/src/logger/pino-logger.module.ts`) — wraps `nestjs-pino`'s `LoggerModule.forRoot()` for structured JSON logging. `level` is `debug` outside `NODE_ENV=production`, `info` in production; pretty-printed via `pino-pretty` outside production only (that package is a devDependency and isn't installed in the production Docker image, consistent with `NODE_ENV=production` there — see `docs/adr/0012`). Redacts `req.headers.authorization`/`req.headers.cookie` (via pino's `redact`) so `pino-http`'s automatic request logging never writes a raw Bearer JWT or cookie to the logs. Imported into every app's root module; every `main.ts` also calls `NestFactory.create(...)`/`createMicroservice(...)` with `{ bufferLogs: true }` then `app.useLogger(app.get(Logger))` so Nest's own bootstrap logs go through Pino too, not just request logs. Replaces the old `LoggingMiddleware` (deleted) — `pino-http`, wired in automatically as part of `LoggerModule.forRoot()`, already logs every HTTP request/response with method/url/status/response time, so a hand-rolled middleware doing the same via `console.log` was redundant. See `docs/adr/0014-nestjs-pino-structured-logging.md`.
- `VersionManagementMiddleware` — rewrites unversioned/unsupported URIs to `/v1` or `/v2`.
- `ProxyService` / `TCPProxyService` / `HttpProxyService` — template-method base classes `api-gateway`'s proxy services extend to translate a downstream failure into an `HttpException`, instead of each hand-rolling its own `toHttpException`. `AuthProxyService`/`InventoryProxyService` extend `TCPProxyService` (RPC error shape); `OrderProxyService`/`ProductProxyService`/`UserProxyService` extend `HttpProxyService` (Axios error shape). See `docs/adr/0009-proxy-service-error-mapping-hierarchy.md`.
- `AuthProxyModule`/`InventoryProxyModule` (`apps/api-gateway/src/modules/`) aren't imported into `AppModule` — `AuthProxyController`/`InventoryProxyController` resolve `AuthProxyService`/`InventoryProxyService` lazily via Nest's `LazyModuleLoader`, memoized on a promise field so the module only loads once. This means the TCP `ClientsModule` client each module registers (to `auth`:8003 / `inventory`:8002) isn't instantiated until the first request actually hits `/auth/*` or `/inventory/*`. `OrderProxyService`/`ProductProxyService`/`UserProxyService` (HTTP/Axios-based, no TCP client) stay eager providers in `AppModule` as before.

Most of these are registered ad hoc per app (not uniformly — `order`/`inventory` don't register the global filter, and only `api-gateway` registers the global interceptor; `user`/`product`/`api-gateway` all register `HttpErrorFilter`, along with Swagger and URI versioning for `user`/`product`, carried over from the old `nest-js-training` reference app). `AppLoggerModule` is the one exception, imported into all six apps uniformly. When adding a new HTTP-facing module, wire `HttpErrorFilter` via an `APP_FILTER` provider the same way `user`/`product`/`api-gateway` do — but don't add `APP_INTERCEPTOR`/`ResponseLoggingInterceptor` to a downstream app that's proxied through `api-gateway`; that stays gateway-only (see `docs/adr/0018`) — and always add `AppLoggerModule` to `imports` plus the `bufferLogs`/`useLogger` pair in `main.ts`.

## Known, intentional limitations

- All four persistence-owning apps (`order`, `inventory`, `user`, `product`) use TypeORM + `better-sqlite3`, each to its own file (`order-db.sqlite`, `inventory-db.sqlite`, `user-db.sqlite`, `product-db.sqlite`, all gitignored) — nothing shares a database. `auth` has no database of its own.
- No key rotation/JWKS story for the RS256 keypair — rotating it means redeploying `auth` (new private key) and every verifying app (new public key) together, coordinated by hand.
- `RolesGuard`/`@Roles(...)` are applied only to the four routes listed under "Cross-cutting conventions" above (product create, user reads, inventory stock update) — every other guarded route still just checks "is this a valid token", not "does this role have permission". See `docs/adr/0010-rbac-role-to-route-mapping.md`.
- No Consul — the `consul` dependency and `api-gateway`'s self-registration were removed once Kubernetes-native service discovery (K8s Services + cluster DNS) was decided as the deployment target. See `docs/adr/0011-drop-consul-for-kubernetes-native-discovery.md`. `api-gateway` still serves `GET /health` (self-liveness only, via `TerminusModule`) for whatever platform health check ends up in front of it (e.g. a K8s readiness/liveness probe).
- Transport is pure `Transport.TCP` with hardcoded ports in each `ClientsModule.register(...)` call — no message broker (Kafka/RabbitMQ/Redis). TCP client *hosts* are env-var-driven (`INVENTORY_SERVICE_HOST`, `ORDER_SERVICE_HOST`, `AUTH_SERVICE_HOST`, `USER_SERVICE_HOST`, each defaulting to `localhost` for local multi-process dev) so Docker Compose/Kubernetes can point them at each other's service name instead — see `docs/adr/0012-containerize-with-docker-compose.md`. Every TCP server (`order`, `inventory`, `auth`, `user`) binds `0.0.0.0`, not `localhost`, so it's reachable from other containers. Each app's SQLite filename and HTTP port remain hardcoded literals, consistent with the project's no-`@nestjs/config` stance; `dotenv` is used only where env vars are already in play (service base URLs in `api-gateway`, the RS256 keypair in `auth`/`user`/`product`/`api-gateway`, and now the TCP client hosts above).
- **The `Transport.TCP` legs are plaintext and `httpsOptions` does not cover them.** Passing `httpsOptions` to `NestFactory.create` wraps only the Express server; `app.connectMicroservice(...)` runs a separate socket server (`order` 8001, `inventory` 8002, `auth` 8003, `user` 8004) that is untouched. The entire order↔inventory and auth↔user flow is therefore unencrypted even with the gateway on HTTPS. See `docs/adr/0017`.
- No CQRS (`@nestjs/cqrs` isn't installed) — order/inventory logic is plain services + `@EventPattern`/`@MessagePattern` handlers.
- `api-gateway`'s `OrderProxyService`/`UserProxyService`/`ProductProxyService` mirror their downstream app's HTTP routes by hand (create/list/get-one/update/delete) — there's no shared route contract, so any new route added to `order.controller.ts`/`users.controller.ts`/`product.controller.ts` must be manually mirrored in the matching gateway proxy controller too. See `docs/adr/0005-api-gateway-sole-entry-point.md` and `docs/adr/0007-proxy-user-product-via-http.md`.
- `user` and `product` remain directly reachable on their own ports (3003/3004) in addition to being proxied through `api-gateway` — nothing blocks calling them directly, this just adds the gateway as the intended front door. See `docs/adr/0007-proxy-user-product-via-http.md`.
- `user`/`product`/`api-gateway` each hand-roll the same Swagger/`VersionManagementMiddleware` bootstrap in their own `main.ts` — no shared helper exists yet.
- `AppLoggerModule`'s Pino logs are structured per-app but not correlated across a request's TCP hops — `pino-http` generates/logs a request ID for the HTTP leg (e.g. `api-gateway`'s inbound request), but that ID isn't threaded through the outgoing `ClientsModule` TCP call, so `order`'s and `inventory`'s logs for the same logical request don't share an ID. Tracing a request end-to-end today means correlating by timestamp/payload, not by ID.

## Architecture Decision Records

`docs/adr/` holds lightweight MADR-style ADRs (Context/Decision/Consequences) — see `docs/adr/README.md` for the index and template. Write a new one whenever a change picks between multiple real alternatives and the choice isn't obvious from reading the code (e.g. where shared code lives, which app owns a cross-cutting concern, what gets deferred vs. built now, a dependency chosen not to add). Skip it for small mechanical fixes. Check `docs/adr/` before making a call that might already be decided there.

## What's next (not yet implemented)

Deliberately deferred pattern work, tracked for a future session: formalizing the messaging/transport layer (typed event payloads, config-driven ports), applying cross-cutting conventions uniformly across all apps + an RPC exception filter for the TCP side, CQRS (`@nestjs/cqrs` command/query/event handlers for order/inventory), a facade layer in front of the CQRS bus, a SOLID pass (repository interface/DI token for order storage, SRP split of `InventoryService.handleOrderCreated`), extracting `user`/`product`/`api-gateway`'s duplicated Swagger/versioning bootstrap into a shared `libs/common` helper, extending `@Roles(...)` coverage to more routes as new permission requirements come in (only product-create/user-reads/inventory-stock-update are gated today, see `docs/adr/0010-rbac-role-to-route-mapping.md`), and propagating a correlation/request ID through the TCP `ClientsModule` calls so `AppLoggerModule`'s Pino logs can be traced across service hops (see the correlation-ID limitation above). Docker Compose (`docs/adr/0012`) is done and is the current deployment story.
