# 0016. Redis-backed HTTP response cache for `user`/`product` reads

Status: Accepted
Date: 2026-08-05

## Context

`user` and `product` each serve read-heavy, rarely-changing GET routes (`GET /users`, `GET /users/:id`, `GET /products`, `GET /products/:id`) sitting in front of their own SQLite file. Nest's docs-era example (`import { CacheModule, CacheInterceptor } from '@nestjs/common'`) no longer applies on Nest 11 — that API moved out of `@nestjs/common` years ago. The current package is `@nestjs/cache-manager` (v3, wrapping `cache-manager` v7's Keyv-based rewrite), and its `CacheModule.register()` options no longer include the old `max` (LRU capacity) knob either — the default memory store isn't bounded, and getting a bounded store back means supplying an explicit Keyv-compatible store yourself.

Two real alternatives existed for the store: `cache-manager`'s default in-memory store (zero new infra, but per-process — each of the two apps' own container/replica would cache independently, and every restart drops it), or a shared Redis store via `@keyv/redis`. Since `order`/`inventory`/`auth` don't have HTTP GET surfaces worth caching (no persistence for `auth`, TCP-only for `inventory`, and `order`'s reads aren't in scope here), only `user` and `product` needed wiring.

## Decision

- Added `libs/common/src/cache/app-cache.module.ts` (`AppCacheModule`, exported via `@app/common`) rather than duplicating `CacheModule.registerAsync(...)` in both apps — same pattern as `AppLoggerModule`. It reads `REDIS_URL` and calls `@keyv/redis`'s `createKeyv(...)` when present; when absent (or `NODE_ENV=test`), it passes no `stores`, which makes `cache-manager` fall back to its own in-memory store — this is what unit tests, e2e tests, and Redis-less local dev use, mirroring how each app's `TypeOrmModule.forRoot` already swaps to `:memory:` under `NODE_ENV=test`.
- Imported `AppCacheModule` into `apps/user/src/user.module.ts` and `apps/product/src/product.module.ts` only.
- Applied `@UseInterceptors(CacheInterceptor)` + an explicit `@CacheKey(...)` per GET route (list and by-id) in `ProductController`/`UserController`, rather than registering `CacheInterceptor` as a module-wide `APP_INTERCEPTOR`. `CacheInterceptor`'s own `isRequestCacheable` already restricts it to GET, but `user.controller.ts` also carries this app's TCP `@MessagePattern` handlers (`VALIDATE_CREDENTIALS`, `CREATE_USER`) in the same class — keeping the interceptor route-scoped makes the cached surface explicit rather than relying on that safety check. Default cache key (request URL) isn't used for the by-id routes either — an explicit `productCacheKey(id)`/`userCacheKey(id)` factory is used instead, so cache entries can be targeted for invalidation without needing to know the exact request URL/version prefix that produced them.
- Default TTL is 10 minutes (`DEFAULT_CACHE_TTL_MS` in `app-cache.module.ts`), applied at the `CacheModule` level rather than per-route `@CacheTTL(...)`. **The unit is milliseconds** — `cache-manager` v7/Keyv take ms, so a bare `600` means 0.6s, not 10 minutes; the constant is `_MS`-suffixed and commented because that mistake reads as "the cache never works" (every request a `MISS`) rather than as an error.
- Because `api-gateway` is the sole client-facing entry point (ADR 0005), the cache status has to be observable *through* it — hitting `user`/`product` directly on 3003/3004 to see `X-Cache` would contradict that pattern. `HttpProxyService.forward()` (in `libs/common`) therefore takes an optional `HeaderSink` and copies the downstream `X-Cache` header onto the gateway's own response before `map(res => res.data)` discards everything but the body. The gateway's `UserProxyController`/`ProductProxyController` read/write routes obtain it via `@Res({ passthrough: true })` — `passthrough` matters, since a bare `@Res()` would switch Nest to manual-response mode and bypass `ResponseLoggingInterceptor`'s envelope.
- `forward()`/`withAuth()` were pulled up from the three hand-rolled private copies in `OrderProxyService`/`UserProxyService`/`ProductProxyService` into `HttpProxyService` itself, so the header-forwarding lives in one place instead of being pasted per proxy — the same consolidation ADR 0009 already applied to `toHttpException`. `HeaderSink` is a structural one-method interface rather than Express's `Response` so `libs/common` stays transport-agnostic.
- `ProductService`/`UserService` inject `CACHE_MANAGER` directly and delete the relevant list + by-id cache key(s) on every `create`/`update`/`remove`, so a write is visible on the very next read instead of waiting out the TTL.
- `docker-compose.yml` gets a `redis:7-alpine` service (named volume `redis-data`) that only `user`/`product` depend on and point `REDIS_URL` at (`redis://redis:6379`). `.env.example` documents `REDIS_URL` with the same "unset falls back to in-memory" note.

## Consequences

- `user` and `product` now share a Redis cache when run via Compose — a write through one replica invalidates what the other replica's readers see, which the old per-process in-memory approach never gave.
- Redis is a new piece of infra for local Compose runs (`docker compose up` now also brings up `redis`), though it's optional for plain `nest start`/Jest — those all silently fall back to in-memory, so no developer workflow breaks by omission of `REDIS_URL`.
- Cache invalidation is manual and per-service (explicit `.del`/`.mdel` calls in `ProductService`/`UserService`) rather than a generic decorator — acceptable at today's scale (2 apps, 4 routes) but doesn't generalize automatically if more cached routes are added; a future pass could extract a shared "invalidate on write" helper if this pattern spreads to `order`.
- Like the JWT keypair (ADR 0008) and TCP client hosts (ADR 0012), Redis has no HA/clustering story here — single container, no persistence guarantees beyond the named volume, consistent with this project's "smallest thing that demonstrates the pattern" scope.
